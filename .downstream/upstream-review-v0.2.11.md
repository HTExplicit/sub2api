## Integration decisions

The owner decided the four high-impact areas on 2026-10-01; all four follow official semantics.

- **In-flight balance reservation (upstream #7681).** Adopted and enabled by default as upstream (`billing.inflight_reservation.*`). Balance-mode requests reserve a priced estimate in Redis after the eligibility check; the billing task takes over the reservation and the balance cache is deducted synchronously before it is released. Estimation or Redis failure fails open; `fail_closed_on_unpriced` stays `false`.
- **API key creation limits (upstream #7752).** Adopted with upstream defaults: 200 active keys per user and 60 creations per user per hour (`api_key_create.*`).
- **Remote Codex model catalog (upstream #7736).** Adopted: Codex tabs default to `model_catalog_url`, with the local catalog file as the alternative and the 1 MiB fallback. The server-side manifest still supplies the catalog and its capacity; capacity stays manifest-derived and is never hard-coded.
- **Claude Code-only groups (upstream #7579).** Adopted verbatim: with a configured fallback group the OpenAI-compatible Chat Completions and Responses entries schedule in that group instead of returning 403. Without one the 403 is unchanged.
- Everything else (GPT-6.1 Sol pricing and constants, Codex subscription plan recognition #7730, Astra Ultrafast capability and pricing, confirmed Claude limit-reset redemption #7726) is the union of upstream additions and downstream contracts, with upstream semantics where both define the same behavior.
- **Claude limit-reset redemption (upstream #7726)** keeps upstream's outcome contract: the redeem response carries only known outcome and reason codes and cleared window names (no grant, organization or upstream request IDs), because an unknown answer fences the organization against a blind retry. What the response drops stays visible to administrators in the logs: every claim that does not end in a definite known result (transport error, non-200 status including 401/403, undecodable body, unknown result, indeterminate or unknown reason) is logged as `claude_reset_claim_upstream` with the account ID, the upstream HTTP status and the raw body (bounded to 2 KiB, not redacted), which reaches the server log and the Ops system log. Echoing that detail in the redeem response and cell is an open owner question, not part of this integration.

## Deliberate downstream deviations kept

- **Capacity stays manifest-derived.** Upstream's GPT-6.1 Sol Codex descriptor embeds the official client entry, including `context_window: 272000` and `max_context_window: 872000`. The locally generated descriptor drops those capacity fields (struct fields and the official-metadata merge in `MarshalJSON`), so GPT-6.1 Sol has no capacity default; the capacity resolver writes it when evidence exists, exactly as for GPT-5.6 and GPT-6 Sol/Luna. Upstream's static `configuredCodexGPT56MaxContext` assignment is not restored. The upstream assertion in `TestGPT61SolOfflineCodexCatalog` that required the embedded window was rewritten to the downstream contract (no `context_window`/`max_context_window`, null `auto_compact_token_limit`). Upstream's OpenCode profile for `gpt-6.1-sol` in `UseKeyModal.vue` also carried a static `limit` (1,050,000 / 128,000); that hunk auto-merged and is removed like every other static OpenCode limit in the v0.2.9 capacity unification (`862e84bbb`), so the exported limit comes only from resolver-tagged manifest rows and the spec asserts it stays undefined otherwise.
- **Unknown GPT-6.x names stay unpriced.** The downstream guard that leaves unrecognized `gpt-6-*` names without a price also covers `gpt-6.*` names other than the recognized GPT-6.1 Sol spellings: dated snapshots such as `gpt-6.1-sol-2026-10-01` (passed through verbatim, see below) and names such as `gpt-6.1-luna` no longer fall back to the `gpt-5.4` default card. Exact price cards (including compact `-YYYYMMDD` dates matched by base name) are still found first; the guard only replaces the default-card fallback.
- **Dated GPT-6 snapshots pass through unchanged (#192), now including GPT-6.1 Sol.** `gpt-6.1-sol` joins the exact Codex model map, but no `codexVersionModelPrefixes` rule is added for it or for Sol/Luna; its finite effort and compact aliases are recognized by `normalizeKnownOpenAICodexModel`.
- **Codex manifest download keeps the ChatGPT-style route.** The fetched and downloaded catalog still comes from `{root}/backend-api/codex/models` without a pinned `client_version`. The remote `model_catalog_url` written into `config.toml` is upstream's version-free `{root}/v1/models`; Codex appends its own `client_version` to that URL (openai/codex `catalog_request_url`), which routes to the same Codex manifest handler.
- **OpenCode keeps the manifest.** The catalog panel and manifest fetch remain available on the `opencode` tab for every platform, because OpenCode capacity is read from resolver-tagged manifest rows.
- **Raw Chat Completions keeps no early ops model write.** The downstream raw Chat Completions path has never set `SetOpsUpstreamModel` before dispatch (kept through every previous integration); only upstream's new GPT-6.1 Sol request validation is added there.
- The fork's scheduler reporting, composite routing (`wsRoutingModel = wsForwardModel`), synchronous cyber session-block write, GPT-5.6 family pricing fallbacks, DeepSeek pricing identity, profit gate, quota-activity tracking, palette C console, stacked table cells, static `data-ui` hooks and `#overlay-root` are untouched.

## Auto-merged areas checked

- **Every gateway handler takes the reservation.** Upstream wires Messages, Chat Completions and Responses (both gateways), Gemini, embeddings, images, web/x search, alpha search, Grok media and voice, OpenAI-platform Messages and the Responses WebSocket (session-level, per-turn billing takes over). Downstream paths reach the same handlers: Image Studio (in-process router to `OpenAIGatewayHandler.Images`), async image tasks, the `/backend-api/codex` Responses, WebSocket and alpha-search routes, Seedance task creation through Grok media, the OpenAI-compatible provider platforms (Kimi, Zhipu, DeepSeek, MiniMax, OpenCode Go), and Cindy accounts, which are served by the OpenAI gateway handlers.
- **Deliberately exempt (no reservation):** token counting, model lists, usage and key billing info, the Codex manifest, Live/realtime calls (identical to upstream; eligibility check only), batch images (separate batch billing flow), media status/content polling and custom voices (zero estimate by design).
- **Balance and pricing composition.** `syncBalanceCacheAfterDeduction` first invalidates an exhausted balance (downstream threshold), otherwise deducts the cache synchronously while reservations are enabled. The estimate uses the same `GetModelPricing` (GPT-5.6 family fallbacks, DeepSeek identity), resolver, channel mapping, user group rate and peak multipliers as billing; time-of-day DeepSeek discounts are not applied to the estimate, so it stays conservative. Overdraft accounting and the profit gate are unchanged.
- **Claude reset redemption (#7726)** renders inside the existing `ClaudeResetCreditsCell`. The irreversible reset button and its confirmation follow `canInteract` like `OpenAIQuotaResetCell`: they appear only in the account details drawer, while the read-only table and card cells keep just the reset-count query they already showed. `redeemed` therefore refreshes usage only in the drawer, which loads its own usage rather than the table's batch. The button matches the console's small ghost-button rule for usage actions, and its confirmation uses the shared dialog in `#overlay-root`.
