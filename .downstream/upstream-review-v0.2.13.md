## Integration decisions

Every official commit is adopted with its official behaviour. Where upstream and a documented downstream contract define the same thing, the downstream mechanism carries upstream's addition.

- **TypeSafe / Jev System One (upstream #7425, the v0.2.12 fixes, #7813).** Adopted: platform `typesafe`, API-key accounts only, `POST /v1/systemone` with model `jev-latest`, not streamed, billed on input tokens only (fallback price 0.042 USD per million input tokens, output 0). A TypeSafe group is rejected on Messages, Chat Completions, Responses and token counting before scheduling, and `/v1/systemone` rejects every other group. The in-flight balance reservation, the profit gate calls and the mandatory usage task of the new handler are upstream's; the usage task goes through the downstream tracked submitter like every other handler.
- **TypeSafe inside downstream mechanisms.** The platform enters the frontend through `CONCRETE_PLATFORM_VALUES` (quota tables, default quota settings, dashboard cards, user quota modal), the `accent()` colour tokens (`sky`) and the generic branch of `GatewayHandler.Models` with `defaultModelIDsForPlatform`; no upstream literal list or TypeSafe-only branch was added next to them.
- **TypeSafe in downstream account flows.**
  - Connection test and batch test: the model resolver returns `jev-latest` for a TypeSafe account (`connectionTestDefaultModels`), so the batch test no longer falls back to a Claude model name. The reasoning-effort resolver offers no effort (the System One wire has none). The quality check stays limited to OpenAI OAuth accounts.
  - API-key model catalog auto-refresh: TypeSafe accounts are not eligible (`UpstreamModelCatalogAutoSyncEligible`). System One has no model list and the sync request builder rejects the platform, so a refresh could only fail and back off.
  - Group capacity catalog: the composite pool is `matchingPlatforms(PlatformComposite)` instead of a second hand-written platform list, so TypeSafe accounts of a composite group contribute their rows. `jev-latest` has no capacity unless an account override or observation supplies one.
  - System prompt injection: not applied. System One has no system or instructions slot and its forwarder calls no injector.
- **Recharge bonus tiers (upstream #7802).** Adopted: `payment_recharge_bonus_tiers`, `payment_recharge_bonus_mode` (`bonus` or `discount`) and `payment_recharge_bonus_notice` in the payment settings, `payment_orders.bonus_amount`, promotion tags and the notice on the recharge page, the bonus in order lists, details and the payment result, and the affiliate rebate base without the bonus. No tier is configured by default.
- **Account priority quick adjust (upstream #7630).** Adopted: the stepper and inline input in the accounts table save a priority-only update 450 ms after the last change, without confirmation, and revert on failure. Downstream table rows open the details drawer on a click, so the cell stops click propagation; without it every stepper click also opened the drawer.
- **Security fixes.** Adopted: the anonymous `POST /api/v1/payment/public/orders/verify` is limited to 20 requests per minute per client IP and fails open on Redis errors (#7673); the Antigravity Gemini path returns a scrubbed Gemini-style error body to the client (#7674); verification-code attempts are counted atomically and password reset tokens are stored as SHA-256 hashes and consumed once (#7676). A reset link issued by the previous version stops working after the upgrade, because its stored token is not a hash; a new reset email is needed.
- **Also adopted as upstream:** Grok CLI identity headers and version gate (#7780), usage settlement when the API key was deleted before billing completes (#7816), API keys sortable by group (#7803), the corrected custom-error-code warning text (#7773), `.github/SECURITY.md` (#7814).
- **Console theme for the new upstream UI.** Behaviour is upstream's; only styling was added under `frontend/src/styles/console`: the eleventh platform segment of the account dialog takes the `sky` identity glyph (`controls.css` 7.1a); the priority control sits as the value of the stacked priority line with label-toned steppers (`pages/accounts.css` 5, reached through the component's own static `data-testid` attributes); the mode toggle of `RechargeBonusTierEditor` carries the static `data-ui="seg-box"` hook. No `:has()`, no runtime-bound hook.
  - One existing rule also reaches the new UI without a change: the `RechargeBonusTierEditor` card has the same header and `p-4` body as the payment provider card beside it, so the positional body rule of `pages/settings-ops-public.css` 2.2 gives it the settings card padding. The comment of that rule now names both cards.

## Migrations

- Upstream files: `241_add_payment_order_bonus_amount.sql`, byte-identical to upstream (adds `payment_orders.bonus_amount DECIMAL(20,2) NOT NULL DEFAULT 0` with `IF NOT EXISTS`), and `241_add_typesafe_platform.sql` (re-creates `user_platform_quotas_platform_check` and `composite_model_routes_target_platform_check` with eleven platforms, `typesafe` included).
- **`cindy` in the quota list of `241_add_typesafe_platform.sql`.** The downstream copy adds `cindy` to the quota list (not to the composite list) and a comment saying so, as the downstream copies of `237_add_minimax_platform.sql` and `238_opencode_go_platform.sql` do. Upstream's file relies on its list being a superset of 238's, and the downstream 238 lists `cindy`. By reading: with upstream's bytes, a downstream database that has not reached 260 and still holds `cindy` quota rows would fail on this file (SQLSTATE 23514, the file's transaction rolls back and startup stops), although the same database upgrades in one start on `v0.2.11-codexrip.8`, where 260 deletes those rows before it re-creates the CHECK. With `cindy` in the list that upgrade stays a single start: the file passes, 260 removes the rows and the value, 265 states the final list. `TestTypeSafePlatformMigration` pins the list. No downstream database has recorded this file yet; from the first release on its checksum is fixed.
- The runner applies unrecorded files in filename order. Both upstream files sort before the downstream `241_minimax_cindy_platform_quota_compat.sql`, `251_user_platform_quota_platform_union.sql` and `260_cindy_openai_apikey_preset.sql`, which re-create the quota CHECK without `typesafe`.
- **Production path (ledger through 263).** The two upstream files are unrecorded and run at the next start, after everything already applied. The quota CHECK left by 260 lists ten platforms and 260 deleted every `cindy` quota row; the composite CHECK left by `238_opencode_go_platform.sql` lists the same ten. Every existing row therefore satisfies both new constraints, and no downstream migration touches `payment_orders.bonus_amount`. Both files succeed by reading; neither was executed against a database here.
- **Final constraints without a downstream tail.** Production would end with the eleven platforms in both CHECKs, plus the retired `cindy` value in the quota CHECK. A new database would run upstream's 241 first and then 241 compat, 251 and 260, ending with ten platforms in the quota CHECK and `typesafe` missing, while the composite CHECK keeps eleven on both paths (no downstream file re-creates it after upstream's 241). With `typesafe` missing, a default TypeSafe quota makes the multi-row quota snapshot of a new user violate the CHECK.
- **Fix.** `265_user_platform_quota_typesafe_union.sql` states the eleven-platform quota CHECK once more at the tail (264 is taken by a separate downstream change that removes the Codex runtime plugin state), so every path ends with the same eleven platforms and without `cindy`: `SET LOCAL` lock and statement timeouts, `DROP CONSTRAINT IF EXISTS` plus `ADD CONSTRAINT`, no row written, no explicit transaction control, a no-op when run again. `TestTypeSafeStaysInTheFinalPlatformChecks` pins the last file that defines each constraint (265 for the quota CHECK, upstream's 241 for the composite CHECK), the eleven platforms and the shape of the tail file.
- **Standing hazard.** Each future upstream migration that re-creates a platform CHECK with a number below the downstream tail needs another tail migration of this kind, and `cindy` in its quota list for as long as a database older than 260 has to upgrade in one start.
- Rollback boundary, by reading: an older image ignores ledger rows of files it does not embed, the extra column has a default and the wider CHECKs accept every older value. TypeSafe accounts, groups and quota rows created after the upgrade are not understood by an older image.
- Generated code: `go generate ./ent` reproduces the merged generated code without a difference. `wire.go` and `wire_gen.go` are unchanged; upstream changed no provider input (the Redis client for the new rate limit is passed inside `router.go`).

## Deliberate downstream deviations kept

- **Connection tests report the upstream text as it is.** Upstream's TypeSafe test sanitized the transport error and cut the response body to 2000 bytes of at most 64 KiB. Downstream it reports `Request failed: <error>` and `API returned <status>: <whole body>` like every other connection test; `TestTypeSafeAccountTestMarksRejectedKey` was rewritten to that contract with a 3000-byte body. The success preview keeps upstream's 2000-byte cut. The test sends no `upstream_model` event: System One answers the `jev-latest` alias with a dated model name, which the batch test would flag as a model mismatch.
- **A connection test passes only on a valid answer.** Upstream's TypeSafe test passes on any HTTP 200 JSON object; its `TestTypeSafeAccountTestUsesPromptAsState` pinned `{"answers":{}}` as a pass. Downstream a connection test needs a valid protocol terminal, and a passed test recovers the account's error and rate-limit state (`RecoverAccountAfterSuccessfulTest` after the single and batch tests, and after scheduled tests with auto-recover), so a relay or a wrong base URL that answers 200 with any JSON must not pass. The TypeSafe test passes only when the response answers the question it asked: `answers.connection_test` of type `noul` with a probability between 0 and 1. `typesafe.NoulScore` checks it with the answer validator `typesafe.Evaluate` applies (now one shared function); the test does not require a `model` field. That answer shape is the one upstream's own client already requires of every content moderation answer; it was not checked against the live API here (no real TypeSafe call). Any other 200 body fails as `Invalid System One response: <reason>: <whole body>` and changes no account state; a body that cannot be read fails as `Failed to read response: <error>`. The two upstream fixtures that passed without a valid answer were given one, and `TestTypeSafeAccountTestRequiresAnswerToItsQuestion` pins the failures.
- **Ops keeps the upstream body of a failed System One request.** Upstream's `handleSystemOneErrorResponse` recorded only the extracted message, which is empty for any body without `error.message`, `detail` or `message`, and its event for a 2xx response the gateway cannot relay recorded only the decoder's error text (`typesafe invalid response` or the size limit error); no log line carried the body, while the client gets a fixed sentence. Downstream both events carry the body bounded by `gateway.log_upstream_error_body` and `gateway.log_upstream_error_body_max_bytes`, as `Detail` and, the events being passthrough, as `UpstreamResponseBody`; the top-level Ops detail follows from the last event, and skip-monitoring passthrough rules see the body as on every other path. The non-2xx path also writes the body log line of `handleErrorResponse`. For the 2xx case `typesafe.DecodeSystemOneResponse` returns the body it read inside a `SystemOneResponseError`; the error text is unchanged and `errors.Is(err, ErrSystemOneResponseTooLarge)` still holds. The client response is unchanged. `TestForwardSystemOneOpsRecordKeepsUpstreamBody` pins the three cases and the switch.
- **Administrators keep the raw upstream error.** The Antigravity masking applies to the client response only. `setOpsUpstreamError` and `appendOpsUpstreamError` still record the upstream message and the raw body as the upstream error detail before the scrubbed body is written. That detail exists while `gateway.log_upstream_error_body` is on (the default) and is cut at `gateway.log_upstream_error_body_max_bytes` (2048 by default). The client error body stored with the same Ops entry is now the scrubbed one.
- **Generic platform lists.** `api/admin/settings.ts`, `api/admin/users.ts`, `UserPlatformQuotaCell.vue`, `UserDashboardStats.vue` and `SettingsView.vue` keep the lists derived from `CONCRETE_PLATFORM_VALUES`. The dashboard cards therefore follow the platform catalog order (TypeSafe after the other known platforms, unknown platforms last); upstream's new dashboard test encoded its literal order and was rewritten to the catalog order.
- **Capacity stays manifest-derived.** Upstream adds no capacity literal in this range and none was added for `jev-latest`.
- **Codex catalogs of composite groups exclude TypeSafe**, as upstream: `compositeAvailableModels(..., includeSystemOne=false)` and the static composite defaults never list `jev-latest`. A group whose own platform is `typesafe` is not covered by that exclusion, also as upstream: `GET /v1/models?client_version=...` reaches `GatewayHandler.CodexModels` for every non-OpenAI group, and its manifest lists `jev-latest` (from the account mappings or `defaultModelIDsForPlatform`), with no capacity unless an account override or observation supplies one.
- Image Studio and the Responses image bridge stay off, the public model page stays retired, the profit control kill switch and the per-account reasoning policy switches are untouched; no upstream change in this range touches them.
